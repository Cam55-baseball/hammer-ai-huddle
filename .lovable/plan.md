# System Inventory — Hammers Modality

A written audit, not code changes. The sweep is already done; this plan is to commit the findings as durable documents you can hand to anyone before new architecture lands.

## What gets written

**`docs/audits/system-inventory-2026-08-23.md`** — the master inventory, eight sections matching your request.

**`docs/audits/inventory/tables-and-columns.csv`** — generated from the live database: one row per column across all 315 public tables (3,820 columns) with type, nullability, default, and whether row-level security is on. Too large for prose; belongs in a file you can sort and filter.

**`docs/audits/inventory/edge-functions.csv`** — one row per edge function: name, purpose, JWT setting, cron status, external services touched.

## Headline findings from the sweep

These are confirmed, not guesses, and will be written up with file paths.

**Scale.** 144 pages, ~130 routes, 78 component folders, ~250 hooks, 315 tables / 3,820 columns (RLS on all 315), ~150 edge functions.

**Integrations actually connected.** Stripe (checkout, portal, webhook, subscriptions). Google Gemini as primary AI with an OpenAI fallback, through a custom wrapper — the code deliberately bypasses the Lovable AI gateway and uses your own keys. Open-Meteo + Zippopotam + Nominatim for weather/geocoding (no key). Remotion Lambda on AWS for rendered video. Resend for email. A Slack webhook for ops alerts.

**Metrics inventory.** 22 distinct scores/indices: MPI, HIE weakness clustering, 13 PIE V2 biomechanical signals, the UHRC six-pillar composite, BQI/PEI/FQI, HPI, Elite Score, the 20–80 grade engine, test-intelligence causal chains, standards tiers, roadmap deltas, pitch recovery clamps, CNS/fascial load, consistency index, steal analytics, Tex Vision, video readiness/tier/confidence, tempo biomech, and RR-6 injury caution. Each gets its file path in the doc.

**Video/camera.** Two independent capture flows — DelayCam (live delayed mirror, client-only) and Analyze Video (upload → pose inference → tempo pipeline → server analysis) — joined by one shared video-moments event bus that drives suggestions. Owner-side upload tooling is a third, separate pipeline.

**Baseball vs softball.** Symmetric data folders on both sides, with real asymmetries: the entire PIE V2 drill/signal/video catalog is baseball-only; pitcher styles are softball-only; Game IQ is authored in baseball and rewritten into softball at render time by a regex voice layer rather than modeled natively; pitch-recovery tables legitimately differ per sport; the two steal engines use different grade vocabularies for the same concept.

**Duplication and drift — the part that matters before new architecture.**

1. Client/server mirrors that have already diverged: foundation thresholds, hitting doctrine, season phase, causal contract, and WIC athlete-context/card-registry exist as hand-copied pairs and a diff shows them different today.
2. WIC is not a mirror at all — ~20 subsystems (dosage, lift, speed, goals, validation, invariants…) exist only server-side; the client copy is a thin shape stub.
3. The nightly MPI job hardcodes copies of tier multipliers, age curves, position weights, and verified-stat boosts instead of importing them.
4. `supabase/config.toml` is missing entries for 45 deployed functions, so they default to requiring a user JWT — including cron/service-role-only jobs and user-facing ones. Only two cron schedules are in version control; the rest were scheduled out-of-band.
5. Three separate Stripe checkout functions, two parallel report pipelines, five overlapping video-analysis functions, nine overlapping pattern/health functions.
6. Frontend: three different `SessionDetailDialog` implementations, two parallel coach component sets, a legacy Progress dashboard nested inside the new one under a colliding name, an apparently dead `SelectRole.tsx`, and three redirect-only legacy routes.

## Technical notes

The CSVs are generated by querying `information_schema` and reading `supabase/functions/*` — no schema or code is modified. The markdown is organised strictly by your eight numbered asks so nothing is buried. Section 8 (duplication/inconsistency) is written as a ranked list with a severity note on each item, since that is what will constrain whatever gets built next; it stops at describing the problem and does not propose fixes.

## Out of scope

No code, schema, migrations, or config are touched. No remediation of any finding listed above.
